# 2026-07-22 Changes and Operating Rules

## Scope

This note records the crawler, timestamp, dashboard, and scheduled-job behavior introduced on
2026-07-22. It is intended to be the operational reference for future changes.

## Code Structure

- Browser launch, cleanup, screenshots, HTML snapshots, captcha handling, and safe DOM text reads are centralized in `crawler/browser_context.py`.
- Post, comment, detail, navigation, and refresh flows reuse these helpers to reduce duplicated `try/except` locator logic and ensure browser resources close on error paths.
- Interaction-count parsing accepts Chinese units plus `w/W`, for example `1.2w` is normalized to `12000`.

## Crawl and Scheduling

- Windows Task Scheduler runs `run_scheduled_once.ps1` every two hours.
- The launcher changes to the project directory and executes `crawler/scheduler.py --once` with the
  configured Python interpreter.
- The scheduler uses deep post crawling: up to six refresh rounds, five scroll passes per round, and
  no early deep-stop until six refresh rounds have produced no new posts.
- Xiaoheihe currently exposes the platform default `????` feed in this community view. The crawler
  records this condition instead of claiming that a `??` option was selected.
- Every scheduled run executes post crawling, timestamp normalization, Markdown generation, HTML
  generation, and Excel export from the current project source files.

## Standard Publication Time

### Motivation

`first_crawl_at` represents when the monitor observed a post, not when the author posted it. It must
not be used as the primary source for publication trends. Historical records also include relative
labels, malformed text, and labels captured from a later refresh.

### Data Fields

The `posts` table and `data/posts.csv` include:

| Field | Meaning |
| --- | --- |
| `publish_time_raw` | Text observed in the page card. |
| `publish_time_crawled_at` | Time when the observed label was read. |
| `first_crawl_at` | First time the monitor stored the post. |
| `standard_publish_time` | Timestamp used for dashboard date filtering and trends. |
| `standard_publish_time_source` | Method used to obtain the standard timestamp. |
| `standard_publish_time_confidence` | Confidence score for the selected method. |

### Deterministic Rules

1. Repair common GBK/UTF-8 mojibake in the raw time label, then parse `N minutes ago`, `N hours ago`,
   `yesterday`, `the day before yesterday`, `N days ago`, `YYYY-MM-DD`, and `MM-DD` forms.
2. Resolve relative times using `publish_time_crawled_at`, or `first_crawl_at` if the observation
   timestamp is missing.
3. If the calculated publication time is later than `first_crawl_at + 10 minutes`, clamp it to
   `first_crawl_at`. This handles later refreshes of the same post.
4. If no usable page time exists, interpolate from reliable neighboring post IDs. Post IDs are
   monotonic enough to provide a bounded temporal estimate between adjacent anchors.
5. If no interpolation anchor exists, use `first_crawl_at` as the explicit last fallback.

The backfill is implemented by `analysis/publish_time.py` and is run by the scheduler before report
creation. It is deterministic: it does not call an LLM and can be rerun safely.

### Source and Confidence Labels

| Source | Meaning | Confidence |
| --- | --- | --- |
| `raw_label` | Directly parsed platform label. | `0.98` |
| `raw_label_clamped` | Parsed label constrained by first crawl. | `0.72` |
| `post_id_interpolation` | Estimated between reliable post-ID anchors. | `0.68` |
| `post_id_interpolation_clamped` | Interpolated estimate constrained by first crawl. | `0.52` |
| `first_crawl_fallback` | No usable label or anchor existed. | `0.35` |

### Initial Backfill Result

The first backfill covered all 788 posts present at the time of the change:

## HTML Dashboard

### Removed Sections

- Core findings.
- Topic distribution.
- Topic summary table.

### Current Sections

1. Summary metrics for posts, positive posts, negative posts, and maximum heat.
2. A combined **publication and sentiment trend** section:
   - A line/area chart for daily publication volume.
   - A theme-river chart for positive, neutral, and negative daily post counts.
3. A high-risk post list.

### Time and Filter Rules

- All dashboard date ranges use `standard_publish_time`.
- The default view is the last 7 days. The **All** button includes the entire database.
- The trend header reports both the number of posts in range and the number whose timestamps are
  estimated rather than directly parsed.
- High-risk posts are filtered by the selected publication-time range, limited to negative posts,
  and sorted by `like_count + comment_count * 3 + (1 - sentiment_score) * 300`.
- The high-risk list displays the standard publication timestamp, engagement counts, sentiment score,
  risk score, summary, and source link.

### Encoding Rule

The HTML generator uses HTML character entities for static Chinese labels and JavaScript Unicode
escapes for dynamic labels. Do not insert non-ASCII literals through PowerShell string replacement;
do so can permanently replace text with `?` on this Windows environment.
